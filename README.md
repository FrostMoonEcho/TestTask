# Acme Platform - DevOps / Platform Engineer Assessment

This repository contains the completed architecture proposal and the hardened
`cell-01` billing-service exercise.

Part A proposes EKS as the long-term production platform. Part B deliberately
keeps and hardens the EC2/K3s runtime supplied by the starter repository;
`No public K8s API` therefore means the Kubernetes API of that K3s distribution.

## Repository layout


## Security design summary

- The K3s EC2 node has no public IP, SSH rule, or key pair.
- The Kubernetes API is reachable only from configured private CIDRs.
- EC2 administration uses AWS Systems Manager Session Manager.
- RDS is private, TLS-enforced, KMS-encrypted, backed up, and deletion-protected.
- S3 uses KMS encryption, versioning, TLS-only access, and full Public Access Block.
- CI uses GitHub OIDC roles instead of AWS access keys.
- Images use immutable commit tags, deploy by exact ECR digest, and are blocked
  on CRITICAL Trivy findings for that digest.
- Helm consumes existing Kubernetes Secrets through `secretKeyRef`.
- The billing-service accepts ingress only from API-gateway pods.

## Prerequisites

- Terraform `>= 1.10`
- AWS CLI v2
- Docker
- Node.js 24 and npm
- Helm 3/4-compatible CLI
- `kubectl`
- Bash and `sha256sum`
- An AWS account with permissions to create the assessment resources
- A pre-created S3 state bucket and DynamoDB lock table
- A private/self-hosted GitHub Actions runner with network access to `cell-01`

The Terraform provider lock file should be generated by `terraform init` and
committed in the real repository.

## 1. Terraform backend bootstrap

The state bucket and lock table must exist before this stack is initialized.
They should have:

- S3 versioning and Block Public Access;
- SSE-KMS encryption;
- a TLS-only bucket policy;
- least-privilege state roles;
- DynamoDB point-in-time recovery;
- CloudTrail logging.

Copy the backend example:

```bash
cp terraform/backend.hcl.example terraform/backend.hcl
```

Replace the account-specific bucket name. The configuration enables native S3
lock files and DynamoDB locking. DynamoDB locking is retained because the
assessment explicitly requires it, although current Terraform marks it as
deprecated.

Initialize and review:

```bash
terraform -chdir=terraform init -backend-config=backend.hcl
terraform -chdir=terraform fmt -check -recursive
terraform -chdir=terraform validate
terraform -chdir=terraform plan -var-file=terraform.tfvars
```

Do not commit `backend.hcl`, real `.tfvars`, state, or plan files.

### Important variables

Copy `terraform/terraform.tfvars.example` to `terraform/terraform.tfvars` and
replace:

- `github_repository` with the exact `owner/repository`;
- `k3s_api_allowed_cidrs` with a private VPN or deploy-runner CIDR;
- the opaque `customer_id`;
- Region/tier values if required.

Never set `k3s_api_allowed_cidrs` to `0.0.0.0/0`.

### Cost note

The example enables RDS Multi-AZ and uses a NAT Gateway. These incur AWS costs.
Destroy testing resources intentionally; RDS deletion protection must be
disabled through a reviewed change before destruction, and a final snapshot is
created.

## 2. Provision `cell-01`

The script validates input, creates a saved plan, records JSONL audit events,
and defaults to plan-only:

```bash
CUSTOMER_ID=customer-001 \
AWS_REGION=eu-central-1 \
TIER=enterprise \
TF_STATE_BUCKET=acme-platform-terraform-state-ACCOUNT_ID \
TF_LOCK_TABLE=acme-platform-terraform-locks \
./scripts/provision-cell.sh
```

Apply the exact saved plan:

```bash
CUSTOMER_ID=customer-001 \
AWS_REGION=eu-central-1 \
TIER=enterprise \
TF_STATE_BUCKET=acme-platform-terraform-state-ACCOUNT_ID \
TF_LOCK_TABLE=acme-platform-terraform-locks \
AUDIT_S3_URI=s3://acme-platform-audit/provisioning \
./scripts/provision-cell.sh --apply
```

Audit output is written to `audit/` and optionally uploaded to the configured
encrypted S3 prefix. The script never enables shell tracing or prints secret
values.

## 3. K3s access

Terraform installs pinned K3s on a private Amazon Linux 2023 EC2 instance with:

- encrypted Kubernetes secrets;
- WireGuard-native Flannel;
- disabled anonymous API authentication;
- no bundled Traefik or ServiceLB;
- kubeconfig permissions `0600`.

Operators use SSM rather than SSH:

```bash
aws ssm start-session --target INSTANCE_ID
sudo k3s kubectl get nodes
```

For a remote private kubeconfig, securely copy the certificate data through an
approved SSM workflow and replace the kubeconfig server address with the
instance private IP. Do not store an administrator kubeconfig in GitHub.

The deploy runner must use a namespace-scoped Kubernetes identity and have the
labels `self-hosted`, `linux`, and `cell-01`. Its kubeconfig path/context are
provided through protected environment variables.

## 4. Secrets and RDS CA prerequisites

The chart expects an externally managed Secret named
`billing-service-secrets` in namespace `cell-01` with these keys:

```text
db-password
jwt-secret
stripe-secret-key
```

Create/reconcile it from AWS Secrets Manager with External Secrets or another
approved controller. Do not put the values in Helm, GitHub variables, Terraform
outputs, or this repository.

`db-password` must belong to the least-privilege PostgreSQL role
`billing_app`. Create that role/grants through the approved database migration
process and store its generated password in Secrets Manager. The application
must not use the RDS master credential managed by Terraform/AWS.

Production uses PostgreSQL `verify-full`. Create the public RDS CA ConfigMap:

```bash
curl --fail --silent --show-error --location \
  https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem \
  --output global-bundle.pem

kubectl --namespace cell-01 create configmap rds-ca-bundle \
  --from-file=global-bundle.pem=global-bundle.pem \
  --dry-run=client -o yaml | kubectl apply -f -
```

The deploy job verifies both prerequisites before running Helm.

## 5. Helm validation and local rendering

```bash
helm lint charts/billing-service \
  --values charts/billing-service/values.production.yaml \
  --set-string env.dbHost=validation.invalid

helm template billing-service charts/billing-service \
  --namespace cell-01 \
  --values charts/billing-service/values.production.yaml \
  --set-string env.dbHost=validation.invalid \
  --set-string image.tag="$(git rev-parse HEAD)"
```

Production hardening includes:

- `runAsNonRoot`, seccomp, read-only root filesystem, and dropped capabilities;
- startup, readiness, and liveness probes;
- resource requests and limits;
- dedicated ServiceAccount with token automount disabled;
- API-gateway-only ingress NetworkPolicy;
- `secretKeyRef` for all sensitive values;
- immutable image tags supplied by CI.
- production image references pinned to the exact scanned ECR digest.

## 6. GitHub Actions configuration

Create a protected GitHub Environment named `cell-01-production`, configure
required reviewers, and restrict deployment branches/tags to the selected
branch `main`. The `environment:` key in the workflow references the gate;
reviewers and the branch restriction are configured in repository settings.

### Repository/environment variables

| Variable | Example/source |
|---|---|
| `AWS_REGION` | `eu-central-1` |
| `AWS_ACCOUNT_ID` | Target 12-digit account ID |
| `ECR_REPOSITORY` | Terraform output path, normally `cell-01/billing-service` |
| `AWS_ECR_PUSH_ROLE_ARN` | `github_ecr_push_role_arn` output |
| `AWS_DEPLOY_ROLE_ARN` | `github_deploy_role_arn` output |
| `KUBECONFIG_PATH` | Protected path on the private runner |
| `KUBE_CONTEXT` | Restricted `cell-01` context name |
| `RDS_ENDPOINT` | Exact `rds_endpoint` Terraform output; environment-scoped |

No AWS access keys are needed. Build and deploy jobs exchange GitHub OIDC tokens
for temporary AWS role credentials. The environment branch restriction is
required because an environment-based OIDC `sub` identifies the environment,
not the source branch.

### Pipeline behavior

On each push to `main`:

1. `npm ci` and `npm audit` run from the committed lockfile.
2. Terraform formatting/validation and Helm lint/template validate the
   infrastructure and production manifests.
3. Docker builds an image tagged with the commit SHA.
4. The image is pushed once to the immutable ECR repository.
5. CI resolves its ECR digest and Trivy scans that exact immutable object,
   blocking CRITICAL OS/library vulnerabilities.
6. The protected environment pauses for approval.
7. The private runner refreshes the short-lived ECR pull secret.
8. CI injects the exact non-secret RDS endpoint from the protected environment.
9. Helm deploys with `--atomic`, `--cleanup-on-fail`, and `--wait`.

The assessment refreshes an ECR image-pull Secret at deployment time. A larger
production K3s fleet should use a continuously reconciled registry credential
or a tested kubelet ECR credential provider so newly scheduled pods can always
refresh short-lived ECR credentials.

## 7. Rollback

Application rollback:

```bash
helm history billing-service --namespace cell-01
helm rollback billing-service REVISION \
  --namespace cell-01 \
  --wait \
  --timeout 5m
```

Images are immutable, digest-pinned, and retained by ECR lifecycle policy, so a
previous Helm revision still references the original image. Database changes
must follow expand-contract migrations; this stub does not include migrations.

Infrastructure rollback is a reviewed forward change. Do not apply an old
Terraform plan after the state or configuration has changed.

## Known limitations

- The assessment runtime is a **single K3s node** and is not highly available.
  Production HA K3s requires three server nodes or should use managed EKS.
- One NAT Gateway is used to limit assessment cost; it is not multi-AZ HA.
- The private GitHub runner/VPN is a documented prerequisite rather than a
  permanently running runner provisioned by this small stack.
- The backend S3 bucket and DynamoDB table are external bootstrap resources.
- The application is a health-check stub and does not exercise real
  PostgreSQL, Redis, S3, payment, or WebSocket behavior.
- Resource requests/limits are safe starting points and require tuning from
  production telemetry.
- The chart assumes an external secret controller and RDS CA ConfigMap.
- Outbound TCP/443 currently uses the NAT Gateway; a production cell should
  add tested VPC interface endpoints and an egress proxy/firewall allowlist.
- K3s installation uses the official install endpoint and a pinned version;
  a production supply chain should mirror and checksum binaries internally.
